# The Playbook — How to Play-Test a Cognitive Ecology

Play-testing is how this project learns. A play-test is a *question about
the kernel asked by building a small organism and watching it live*. It
is not a unit test (those live in `tests/` — they check laws) and not a
benchmark (those measure; play-tests *discover*). Every example in
`examples/` began life as a play-test.

## The loop

1. **Pick a scenario** — copy `templates/scenario_template.md`. The
   template's catalog lists eight seeded scenarios (games, health,
   finance, education, science, devops, home, agriculture) generated by
   dogfooding Hy4-preview; each names the failure mode most worth
   watching.
2. **Write the hypothesis** — one falsifiable sentence: "If X, then the
   organism will Y by tick N." "We'll see what happens" is not a
   hypothesis.
3. **Build small** — start from `templates/agent_template.py`. One WHY
   root, 2–3 tensions, 3–5 scripts. A play-test that needs twenty
   scripts is three play-tests.
4. **Run with telemetry** — `scripts/run_rounds.py --ticks 300 --out
   runs/exp1` writes per-tick JSONL (`ran`, `starved`, `slept`,
   `tensions`, `conservation_ok`) plus full state and event logs.
5. **Read the right dials** (below), then **write down the surprise** —
   the part that did not match your hypothesis. The surprise is the
   finding; everything else is confirmation.
6. **Feed findings back** — kernel bugs → issues; concept gaps → docs;
   good scenarios → `examples/`.

## The dials worth reading

| Dial | Where | What it tells you |
|---|---|---|
| Conservation | `report.why` / telemetry `conservation_ok` | the law held; if this ever fails, it's a kernel bug |
| Attention distribution | `market.stats()` clear_rate + `most_starved` | is the market actually deliberating, or is one organ a tyrant? |
| Script demography | `ecology.alive()` vs `ecology.necrology()` | births, deaths, generations — a healthy ecology has turnover |
| Tension time-series | telemetry `tensions` per tick | homeostasis should *oscillate*; pinning at 0 or 1 is a diagnosis |
| Sleep accounting | `rt.sleeper.stats` | replay/prune/dream counts; an organism that never sleeps is never idle (suspicious); one that always sleeps is dead inside |
| Event growth | `len(rt.bus)` per tick | runaway growth means noisy actions; flatline means nothing lives |
| WHY necrology | `rt.why.necrology()` | every purpose transition, with reasons — the audit trail |
| Cache economics | `StablePrefixSession.stats()` | hit rate + est. savings for LLM organisms |

## What we learned play-testing this build (2026-10-31)

Kept honestly, the findings log is the most valuable doc in the repo.
From building the current examples:

- **The veto law was missing.** (example 01/05) The market happily
  cleared zero-attention bids when nothing else was running — a sated
  drink script kept drinking forever. Fixed: attention-0 bids never
  clear, and `test_vetoed_bids_never_clear_even_in_an_empty_market`
  pins it.
- **Successful children can starve their own parent.** (mock LLM agent)
  Spawned scripts' success rates rose above the proposer's accept rate,
  so the LLM proposed exactly once and never again. Fixed with a
  staleness term in the proposer's urgency — "boredom with one's own
  repertoire" — and `search` became honestly one-shot (re-charting a
  charted topic fails, so EV falls).
- **Dream mutations collided on names.** (sleep test) Dreaming the same
  parent twice raised `duplicate live script name`. Fixed by
  generation-counted unique names.
- **A nag needs a threshold, not a drive.** (example 05) A check-in
  script keyed to a growing tension nagged every tick. Giving it
  `when: tension_above 0.20` produced manners: it nags at ticks 3, 6, 9
  — and not otherwise. Trigger design *is* politeness design.

Each of those is now a test, a doc paragraph, or both. That is the loop
working.

## Habits

- **Determinism first**: fix the seed; report the seed. A finding you
  cannot reproduce is a rumor.
- **Kill something every session**: a WHY root, a tension, a component.
  Ecologies prove themselves in how they degrade.
- **Watch the starved, not just the winners**: `most_starved` is where
  design friction accumulates.
- **Small steps**: one variable per run. The kernel is deterministic —
  respect that power.
- **Write the scenario up** with `templates/scenario_template.md`, even
  the failures — especially the failures.
